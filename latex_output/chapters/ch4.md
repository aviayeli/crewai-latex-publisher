\chapter{פרוטוקול הקשר המודל}

\section{MCP כממשק מתוקנן}

פרוטוקול הקשר המודל (Model Context Protocol, MCP) מהווה ממשק מתוקנן המאפשר לסוכני LLM לגלות, להפעיל ולתקשר עם כלים בצורה עקבית ותאימה. על ספקט של מערכות אג'נטיות, MCP משמש כ-"USB-C לכלים"—סכימה אחידה המחברת בין מגוון רחב של ממשקי API, מסדי נתונים ושירותים בקרות משותפת.

התקן MCP מגדיר שלושה עמודי שדרה חיוניים: תגלית כלים (tool discovery), סכימת פרמטרים (parameter schema), וניתוח סמנטי של יכולות. כל כלי נרשם בשרת MCP עם תיאור מפורט, רשימת פרמטרים מתקבלים, וסוגי פלט צפויים. כך, אג'נט משימוש בשרת יכול לשאול: "אילו כלים זמינים? מה הן הדרישות שלהם? מה הם מחזירים?"

\cite{perplexity_agent_mcp_2024a} מבהיר כי MCP מתקנן את \textenglish{interface} הכלים אך לא את הלוגיקה של תיאום ביצוע—ההחלטה \textit{איזה} כלים להפעיל בסדר זה או אחר נשארת באחריות מערכת התיאום (הסוכן או הארכיטקטורה הגבוהה). זה חיוני: בשרת MCP אפשר להגדיר "כלי A חייב לרוץ לפני כלי B", אך המקרה הכללי הוא שהשרת מספק רק כלים, והאג'נט מחליט על הסדר.

שטח שמקדם מתקנן זה הוא גמישות. סוכן עשוי להתחיל עם חמישה כלים מוקומיים ולהוסיף שרת MCP ריחוק בעלות כמעט אפס—כל עוד השרת תואם לתקן. זה מאפשר קנה מידה ממוגבל של יכולות ללא שינוי בלב הסוכן.

\section{לולאות סוכן מונחות MCP}

בהקשר MCP, לולאת הסוכן מתקבלת על הצורה הבאה:

\begin{enumerate}
\item \textbf{אתחול}: הסוכן מתחבר לשרת MCP ומשיג רשימה של כלים זמינים—שמם, תיאור, סכימה.
\item \textbf{תכנון}: בהתאם לבעיה בהנוגע למטרה, LLM בחוזרות בוחר כלים רלוונטיים ובונה קריאה.
\item \textbf{הפעלה}: הסוכן שולח קריאת כלי לשרת MCP עם פרמטרים; השרת מריץ את הכלי ומחזיר תוצאה.
\item \textbf{הנמקה}: הסוכן משקל את התוצאה ובוחר לעצור, להפעיל כלי נוסף, או לתקן את הקריאה.
\item \textbf{ירידה}: החזרת תוצאה סופית למשתמש.
\end{enumerate}

דפוס זה אפשר תיאום מבוקר של צעדים מרובים. \cite{perplexity_agent_mcp_2024b} מתאר ארבע דפוסי תיאום שנתמכים על ידי MCP:

\textbf{דפוס 1—רמזי התאמות סכימה:} השרת מספק תיאור מילולי ("כלי B דורש פלט של כלי A כקלט"). הסוכן קורא את התיאור ובנוי מנעות חזרה חוקי.

\textbf{דפוס 2—סדר כפוי בשרת:} השרת חוזר עם כלים בסדר מוגדר מראש או דוחה קריאות שמפרות תלויות (מולתול, הסוכן מנסה קריאה לכלי B לפני A, השרת אומר "זה לא חוקי עדיין").

\textbf{דפוס 3—זרימות משימות בתיאום:} שרת MCP או פלטפורמה המארחת מגדירה משימות/מתכונים (recipes) מראש—"כדי לעשות X, הרץ כלים בסדר כזה". הסוכן פשוט בחר משימה, והתיאום מתבצע באופן אוטומטי.

\textbf{דפוס 4—תיאום רב-סוכנים:} שרת MCP שנתמך על סוכנים מרובים קבוצות, ודגים לתוזק כלים דורך לבחירה מחדש. סוכן A עשוי לקרוא לכלי מסוכן B כחלק מלולאה מורכבת.

כל דפוס מתאזן בין גמישות להבטחה. דפוס 1 גמיש אך דורש ממודיעות סוכן. דפוס 3 מחזק ביטחון אך עלול להוביל להגבלות.

\section{יתרונות וקנה המידה של MCP}

יתרונות MCP כממשק מתוקנן נלקחים בשלוש תחומים עיקריים:

\textbf{תאימות:} תקן יחיד משמעותו שסוכן MCP יכול לתקשר עם שרתי MCP משונים—מחשוב ענני, בסיסי נתונים מקומיים, API צדדים שלישיים—ללא שינוי בלב הסוכן. זה מיתון עלויות פתוח והתחזוקה.

\textbf{קנה מידה:} כשארגון גדל, ניתן להוסיף שרתי MCP חדשים ללא שינוי בתוכנה המרכזית. ניתן לתחזק שרתים בנפרד, לעדכן אותם בקצב שונה, ואף להחליף בהם ללא הפסקה.

\textbf{אבטחה ותצפית:} ממשק מתוקנן משמעותו שניתן לאפליק מדיניות אבטחה באופן אחיד. לדוגמה, הנהלה מרכזית יכולה להגדיר: "כל קריאות כלים צריכות להילקח דרך חתימה דיגיטלית ורישום מלא." שרתי MCP יכולים להאריך דרך זה תוך עמידה בתקן.

\cite{perplexity_cybersecurity_agentic_2024b} מתריע כי אדריכליות משותפות-כלים (כמו MCP) מריכזות סיכון—שרת MCP פגום עשוי להשפיע על סוכנים רבים. אך הסטנדרט עצמו משפר זאת על ידי אפשור:

\begin{itemize}
\item \textbf{בדיקות חתימה}: שרתי MCP יכולים להיות חתומים קריפטוגרפית. סוכנים בודקים חתימות לפני הפעלה.
\item \textbf{גרסה ונעילה}: סוכן יכול להיות מוגדר לשימוש רק בגרסה ספציפית של שרת MCP, למניעת התקפות על ידי שדרוג לא רצוי.
\item \textbf{רישום מרכזי}: כל קריאות כלים עוברות בנקודה מרכזית אחת; ניתן לנתח נתונים בדיעם למאפיינים של ניסיון.
\end{itemize}

בסך הכל, MCP מהווה תשתית ביסודית לתיאום בטוח וקביל של כלים בסוכנים מודרניים. היא מטעמי רוחב וטור מאפשרת לארגונים להתחיל קטנים, להרחיב בכללים ברורים, ולהשמור על בקרה אבטחתית לאורך כל הדרך.
